团队资产的
安全上下文

TeamVault 是一个面向小团队的自托管资源管理平台：把系统入口、项目资料、账号凭据、文件、成员权限、外部分享和审计记录放进同一个可解释的权限上下文中。它的价值不在于“又做了一个网盘”，而在于把散落信息变成可授权、可追踪、可交付的团队资产。

01 / PROBLEM

项目解决什么问题

小团队真正缺少的往往不是“存文件的地方”，而是一个能说明资产属于谁、谁能看、谁能下载、谁能分享，以及发生过什么的统一上下文。

× 传统状态

  • 服务器地址在聊天记录，密码在个人备忘录，文档在多个网盘。
  • 成员离职后难以确认还掌握哪些入口与凭据。
  • 分享文件通常只有“链接”，没有到期、次数和内容范围约束。
  • 项目交付时需要手工整理网址、账号、说明书与附件。
CONTEXT

✓ TeamVault 状态

  • 以“资源”为中心聚合环境链接、凭据、文件、标签与负责人。
  • 用户和小组共享同一权限模型，查看、密钥、文件、下载、编辑、分享分别授权。
  • 外部分享附带密码、有效期、最大访问次数和逐项白名单。
  • 敏感操作形成审计记录，交付和追责都有依据。
BUSINESS

减少信息摩擦

用户不需要记住“某个账号在哪条群消息”，只需进入对应资源模块，就能看到被授权的全部上下文。

SECURITY

把权限落到动作

不仅区分管理员和普通用户，还把资源查看、凭据查看、文件预览、下载、编辑、分享拆成独立能力。

DELIVERY

形成可控交付包

按资源或文件创建临时分享，限定文件和凭据范围，使外部协作不必创建内部账号。

02 / DOMAIN

业务领域与功能地图

项目的核心聚合根是 Resource。网站、工具、项目、知识库、个人空间都被建模为资源类型，文件、凭据和链接作为资源的下级内容。

核心聚合

统一资源库

项目、工具、知识、网站、个人空间；支持标签、敏感等级、可见范围、收藏、软删除与恢复。

敏感数据

账号与凭据

密码、API Key、Token、SSH、数据库、Access Key、TOTP 等；密文存储，查看和复制单独审计。

内容资产

文件与预览

流式上传、SHA-256、路径约束、Range 下载，以及 PDF、PPTX、表格、Word、媒体等只读预览。

访问治理

用户与小组

用户状态、管理员、组成员与组管理员；资源授权支持 USER / GROUP 两种主体。

环境拓扑

资源链接

为资源记录网站、外部文档和其他环境入口，可继承资源权限，也可限制到指定成员或小组。

外部协作

受控分享

资源或单文件分享，支持密码、过期时间、最大浏览次数、文件/凭据白名单和撤销。

可追溯

审计日志

登录、资源变更、凭据查看/复制、文件上传/预览/下载、分享和权限变化等操作留痕。

个人效率

工作台与备忘

权限感知的资产统计、最近更新、收藏和私有/团队备忘，形成日常使用入口。

09 / SECURITY

安全模型与信任边界

安全不是一个 AES 函数。TeamVault 的安全链由身份、权限、数据保护、分享约束、输入边界和审计共同组成。

身份认证Argon2id 密码哈希；随机会话 Token；数据库只保存 Token Hash；HttpOnly / SameSite Cookie。
资源权限管理员 → 所有者 → 基础可见性 → 用户直授 → 小组授权；直授记录优先于组授权。
内容权限资源可见不等于凭据可见；受限凭据与受限链接拥有独立主体白名单。
凭据保护AES-256-GCM + 随机 IV + Auth Tag；密文格式带 v1，明文仅在获准查看时服务端解密。
文件边界扩展名白名单、大小限制、随机存储名、安全路径约束、流式传输、nosniff 与同源策略。
外部分享Token Hash、密码 Hash、HMAC 访问证明、到期/撤销/次数、逐文件与逐凭据白名单。
行为追踪查看/复制秘密、下载、分享、权限变化等敏感动作写入审计；记录 IP 与 User-Agent。
重要认知：“禁止下载”不是 DRM。只要浏览器能预览完整文件，具备技术能力的用户就可能保存响应内容。它能约束产品入口和审计语义，不能从密码学上阻止复制。

建议定位：中小团队自托管平台
为什么选 SQLite，而不是一开始就 PostgreSQL？
强回答：目标用户是单机或单节点的小团队，SQLite 让部署、备份和恢复成本最低；WAL、外键和事务足够支撑当前写入规模。代价是多节点和高写并发受限，当出现水平扩容、集中审计或跨服务事务需求时，再迁移 PostgreSQL。
为什么不用微服务？
强回答：资源、权限、凭据和分享存在强事务关系，当前团队规模和运维能力不需要网络边界。模块化单体保留代码边界，同时避免服务发现、分布式事务、链路追踪和多套部署。未来最先拆出的应是文件/预览或审计，而不是按表拆服务。
如何防止 IDOR（修改 URL ID 越权）？
强回答：不依赖页面隐藏按钮。Route Handler 和 Server Action 都用当前会话重新查询目标实体，再通过 resourceId 执行 canViewFile、canDownload、canEdit 等权限判断；分享链还校验目标类型、资源归属和 fileIds 白名单。
为什么数据库只存分享 Token Hash？
强回答：分享 Token 类似临时密码。若数据库泄露，保存明文会立即暴露所有有效链接；保存 SHA-256 后，服务端仍可通过请求 Token 计算 Hash 查询，但攻击者不能直接从库中复制可用链接。
AES-256-GCM 比普通 AES-CBC 好在哪里？
强回答：GCM 同时提供机密性和完整性，认证标签能发现密文被篡改；每次随机 IV 避免相同明文产生相同密文。当前格式还加入版本号，为未来轮换算法保留空间，但主密钥轮换仍需要独立设计。
浏览器预览为什么不使用 LibreOffice？
强回答：需求只有只读预览，不要求编辑和绝对保真。浏览器解析让上传立即返回，减少转换 Worker、失败重试、缓存和容器体积；代价是 PPTX/DOCX/Excel 的复杂格式可能降级，因此项目设置资源上限和明确下载兜底。
如果用户量增长 100 倍，先改什么？
强回答：先用指标判断瓶颈。典型顺序是：权限查询批处理和缓存 → 文件迁移对象存储/CDN → 数据库迁移 PostgreSQL → 应用无状态化多副本 → 审计/异步任务进入可靠队列。不会因为“可能增长”提前拆成微服务。

12 / DEPLOY

直接可用的生产发布方案

生产服务器不应承担依赖下载和应用编译。针对服务器访问 GitHub、npm 与 Debian 官方源较慢的环境，推荐在开发机或 CI 中构建 Linux 镜像，再把不可变镜像交付给服务器直接运行。

结论：当前最合适的是“预构建 Docker 镜像 + TAR 离线交付”；发布频率提高后，再迁移到 Harbor 或可访问的私有镜像仓库。不要在生产机长期使用 docker compose up -d --build。
01 / BUILD开发机容器构建在 Docker 内生成 linux/amd64 镜像，确保 better-sqlite3 等原生依赖属于 Linux。
02 / EXPORT导出版本镜像用明确版本号保存为 TAR；镜像中不放 .env、数据库或用户文件。
03 / TRANSFERSCP 上传服务器传输单个可校验制品，避免生产机访问外部源码和软件源。
04 / LOAD服务器导入docker load 后，本地镜像已经包含运行所需应用与依赖。
05 / RUNCompose 直接启动生产 Compose 只引用 image，不保留 build；数据继续落在宿主机卷。
不推荐 / 源码构建

生产机执行 --build

  • 依赖 GitHub、npm、Debian 等外部网络
  • 首次安装 gcc、Python 和 Node 依赖耗时不可控
  • 构建工具进入生产流程，故障面更大
  • 同一次发布难以保证制品完全一致
推荐 / 镜像交付

Build once, run anywhere

  • 生产机只需要 Docker 和 Compose
  • 镜像可以校验、归档、复用与回滚
  • 应用镜像与 SQLite/文件数据相互分离
  • 发布失败时切回上一个 image 标签即可

C. 生产 Compose：只运行镜像，不在服务器构建

docker-compose.prod.yml
services:
  teamvault:
    image: teamvault:1.0.0
    container_name: teamvault
    restart: unless-stopped
    ports:
      - "3030:3030"
    environment:
      TEAMVAULT_APP_ROOT: /app
      TEAMVAULT_DATABASE_PATH: /app/data/teamvault.db
      TEAMVAULT_MASTER_KEY: ${TEAMVAULT_MASTER_KEY}
      TEAMVAULT_SESSION_DAYS: ${TEAMVAULT_SESSION_DAYS:-14}
      TEAMVAULT_SECURE_COOKIE: ${TEAMVAULT_SECURE_COOKIE:-}
      TEAMVAULT_ADMIN_USERNAME: ${TEAMVAULT_ADMIN_USERNAME:-admin}
      TEAMVAULT_ADMIN_DISPLAY_NAME: ${TEAMVAULT_ADMIN_DISPLAY_NAME:-TeamVault Admin}
      TEAMVAULT_ADMIN_PASSWORD: ${TEAMVAULT_ADMIN_PASSWORD}
    volumes:
      - ./data:/app/data

上线前检查

01使用 linux/amd64 构建，不能把 Windows node_modules 复制到镜像。
02生产 Compose 不包含 build: .，启动命令也不再添加 --build。
03.env 不打进镜像、不随 TAR 分发；主密钥和管理员密码只保留在服务器。
04升级时必须保留原 TEAMVAULT_MASTER_KEY，否则已有加密凭据无法解密。
05升级前备份整个 data 目录，并验证数据库与 files 同时可恢复。

13 / LIMITS

当前边界与改进优先级

能主动指出边界，比声称“高并发、高安全、零数据丢失”更有工程可信度。下面按风险和学习价值排序。

P0 / 治理

主密钥没有轮换机制

所有凭据依赖单个环境变量主密钥；一旦丢失无法恢复，一旦泄露需要重加密。

建议

加入 keyId、双密钥读取、后台批量重加密、恢复密钥与 KMS/Vault 接口。

P1 / 一致性

文件系统与数据库双写

上传先落盘再写库、删除先删文件再删库，中途失败会产生孤儿文件或失效记录。

建议

临时状态 + 提交/补偿、定期一致性扫描、删除墓碑与可恢复回收站。

P1 / 安全

MIME 与 SVG 边界

上传主要依赖扩展名白名单，MIME 来自客户端；同源内联 SVG 需要额外防御主动内容风险。

建议

魔数检测、SVG 清洗或独立静态域、严格 CSP、危险格式默认 attachment。

P1 / 质量

自动化测试资产不足

仓库未形成系统化测试目录；当前全量 lint 还有既有 no-explicit-any 错误。

建议

优先补权限矩阵、分享次数、Range、加密格式和迁移回滚测试，再做浏览器端核心路径。

P2 / 性能

部分逐项权限查询

单资源权限检查会遍历组并查询授权，资源详情也存在逐凭据判断，规模增长后可能出现 N+1。

建议

统一批量策略解析器、请求级缓存、权限快照或物化结果，并用查询指标验证。

P2 / 合规

审计采用 best-effort

writeAudit 捕获异常后主业务继续，提升可用性，但严格合规场景可能丢失关键审计。

建议

关键操作事务内写审计或 Outbox；为审计失败设置指标、告警和补偿任务。

P2 / 扩展

单节点数据与本地文件

SQLite + 本地卷非常适合当前目标，但不适合多副本同时写和跨机高可用。

建议

定义迁移触发指标；需要多节点时转 PostgreSQL、对象存储和无状态应用。

14 / ROADMAP

可借鉴的演进方案

演进不是“把所有技术都加上”，而是在业务量、风险和团队能力达到阈值时替换对应边界。

阶段 A · 当前

可信单机版

  • Next.js 模块化单体
  • SQLite WAL + 本地文件卷
  • Docker Standalone
  • 浏览器端只读预览
  • 重点：测试、备份、密钥轮换
阶段 B · 团队增长

单服务增强版

  • PostgreSQL 或继续 SQLite 但强化指标
  • S3/MinIO 对象存储
  • Redis 仅用于明确的限流/缓存场景
  • 审计 Outbox 与后台任务
  • 统一权限策略解析器
阶段 C · 多节点

平台化部署

  • 无状态 Web 多副本
  • PostgreSQL 高可用
  • 对象存储 + CDN
  • KMS/Vault 管理密钥
  • 集中日志、指标、Trace 与告警
拆分原则：先用可靠性和性能数据找到瓶颈，再拆边界。文件服务和审计流水通常比“用户服务”更早具备独立部署价值，因为它们的存储、吞吐和可靠性模型明显不同。
15 / PITCH

90 秒项目表达

这段表达适合面试开场。随后根据面试官兴趣进入权限、加密、文件预览或部署细节。

把“做了什么”讲成“为什么这样设计”

“TeamVault 是我为小团队设计的自托管资产管理平台。它解决的是项目地址、账号凭据、文件和交付链接分散的问题。技术上我使用 Next.js App Router 做模块化单体，以 SQLite 和本地文件卷降低部署成本；密码使用 Argon2id，会话和分享 Token 在数据库只保存 Hash，业务凭据使用 AES-256-GCM 加密。权限不是简单角色判断，而是用户/小组与查看、密钥、文件、下载、编辑、分享六种能力的矩阵。文件通过鉴权后的 Range 接口流式返回，PDF、PPTX、Excel、Word 和媒体在浏览器只读预览，因此不依赖 LibreOffice。当前系统适合单节点小团队，我也明确保留了它的边界：主密钥轮换、文件与数据库双写一致性、系统化测试和多节点能力是下一阶段重点。”
